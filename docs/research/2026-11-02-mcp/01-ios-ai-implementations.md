# iOS/iPadOS MCP chat implementation research

Checked 2026-11-02 (UTC). Scope: public Apple-platform AI chat projects with actual remote Model Context Protocol (MCP) Streamable HTTP client/tool execution code, suitable as references for BraisenlyAI imported by Askenly. No repositories cloned; no dependencies, models, or local source code written. Findings distinguish source-verified behavior from README-only claims.

## Recommendation

Use the official [modelcontextprotocol/swift-sdk](https://github.com/modelcontextprotocol/swift-sdk) for protocol transport and lifecycle, and study ETOS LLM Studio for a current, extensive app integration and governance/UI model. Its GPL-3.0 license requires legal review before copying source into a differently licensed app. CopilotChat is the most compact readable custom client but is a lower-confidence implementation template: its `MCPClient` pins `2025-03-26`, has narrow SSE parsing, and flattens results to text. MIT permits reuse subject to preserving notices and license terms. Prefer adapting concepts and tests; copy individual code only after confirming license compatibility and reviewing the exact pinned source.

## Strongest verified projects

### 1. ETOS LLM Studio — strongest complete integration reference

- Repository: [Eric-Terminal/ETOS-LLM-Studio](https://github.com/Eric-Terminal/ETOS-LLM-Studio); native Swift iOS/iPadOS app, Apple Watch app, and shared Swift core. README reports frequent activity; API latest commit checked: `5118339154110e42bb301cac3e0514757de72e30`, 2026-10-31 16:40:30 UTC (latest commit message concerned chat toolbar configuration, not MCP).
- License: GPL-3.0, confirmed repository license metadata/README. Reuse means GPL obligations; do not transplant code without confirming compatibility for BraisenlyAI.
- MCP dependency/revision: README states official Swift MCP SDK; `ETOS LLM Studio.xcworkspace/xcshareddata/swiftpm/Package.resolved` was not inspected, so exact SDK revision is unverified. README claims remote MCP, Streamable HTTP/SSE, reconnect, timeout, handshake management, metadata refresh, resource/template/prompt access, capability negotiation.
- Exact source: [`MCPManager` in `MCPManager.swift` at latest repo commit](https://github.com/Eric-Terminal/ETOS-LLM-Studio/blob/5118339154110e42bb301cac3e0514757de72e30/ETOSCore/ETOSCore/MCP/MCPManager.swift) (file blob SHA seen on `main`: `043d8dab1e6c8182ff1eb380b4a71aad0594651f`). Verified `MCPManager` owns per-server clients/transports, connection states, in-flight connections, cancellation, retry policy, timeout, cached tools/resources/templates/prompts, server notification relay, tool-call tracking, approval/governance logs, and refresh of negotiated protocol version. Its configuration constructs an SDK transport (`server.makeSDKTransport(...)`) and initializes `MCPClient` with client capabilities, sampling and elicitation handlers.
- Tool/history/UI: README describes tool selection by server, per-tool enablement and approval, chat tool toggle, approval policy, and tool results/governance surfacing. Source inspection confirmed published observable `tools`, `activeToolCalls`, `progressByToken`, status, output/error, and log state; full chat renderer was not inspected.
- Auth: README documents secure local DB/Keychain security for app data but exact remote MCP HTTP credential field/storage and OAuth flow not inspected. Do not infer OAuth support.
- Reusable: mostly architectural patterns (SDK boundary, server lifecycle/state/cache, approval, cancellation, retry, observable progress) rather than wholesale app code due GPL and large app-specific persistence/concurrency surface. Strength: closest source-verified match for production-like lifecycle breadth. Gap/risk: exact pinned SDK version, remote auth details, tool-loop/history renderer need targeted follow-up; extensive code increases extraction cost.

### 2. CopilotChat — clearest small custom remote client

- Repository: [jason5545/CopilotChat](https://github.com/jason5545/CopilotChat); SwiftUI iPhone/iPad/macOS, repository requires iOS 26+. Latest commit checked: `d4b81ca90e6d36809ea0241196743ef6f2163f90`, 2026-04-19 09:20:45 UTC. No newer release observed; repo appears small (126 commits in page snapshot; 1 star at check time).
- License: MIT, confirmed GitHub license page.
- MCP revision/transport: direct custom JSON-RPC over Streamable HTTP-compatible POST/SSE. `MCPClient.initialize()` hardcodes `2025-03-26`. It uses `Mcp-Session-Id` and checks JSON vs `text/event-stream`. This is a `2025-03-26` transport implementation, not evidence of current 2025-11-25 or later compatibility.
- Exact source: [`MCPClient` at latest commit](https://github.com/jason5545/CopilotChat/blob/d4b81ca90e6d36809ea0241196743ef6f2163f90/CopilotChat/Models/MCPClient.swift) (current file blob SHA `454442d927ba1e1af673cde2765cce24742c8341`). Source inspected: `connect`, `initialize`, `listTools`, `callTool`, `sendRequest`, `performHTTPRequest`, `parseSSEResponse`. Custom headers are injected into requests; server session ID retained; MCP tools/calls are exposed to chat. `CopilotService.completionLoop` runs up to 10 chat / 50 coding tool iterations, checks per-call permission, executes, appends tool messages, and loops; source builds next provider request history from assistant tool calls and corresponding tool outputs.
- Auth: README states custom headers (example bearer authorization) stored in Keychain; no OAuth flow verified. Tool permissions tiered by tool/server/session.
- Tool/result/UI: server management UI in `MCPSettingsView`; automatic function-call execution in chat; `callTool` extracts text blocks, otherwise serializes JSON. Chat history retains assistant calls + tool result messages. Good small reference for app-level model-to-MCP bridge and permissions.
- Strength/gaps: MIT and readable custom code make narrow reuse plausible. But protocol version is stale; SSE parsing scans complete response text line-by-line, only matches `data: ` lines, text-only extraction loses images/audio/structured content, JSON parsing fallback silently substitutes empty args, no SDK-managed capabilities/negotiation/reconnect/stream resumption/version fallback verified. Treat as a concept/reference, not protocol base. Exact commit is old (April); recheck before any adoption.

### 4. OpenClient — mobile chat, MCP tools are backend-mediated

- Repository: [ArtCC/openclient-llm](https://github.com/ArtCC/openclient-llm); iOS/iPadOS/macOS; AGPL-3.0. GitHub repository search reported push on 2026-11-02 (repo search result at check time; exact HEAD commit and source code not fetched).

- Classification: useful for backend-mediated tool UX and multi-platform chat concepts only. No direct source reuse recommendation for MCP transport; code and tool loop were not verified.

## Protocol and SDK evidence

- Context7 lookup resolved `/modelcontextprotocol/swift-sdk`; query returned official Swift SDK docs for `HTTPClientTransport`, `listTools()`, `callTool(...)`, and content handling. `HTTPClientTransport` accepts endpoint, URLSession configuration, `streaming`, protocol version (docs default `Version.latest`, `2025-11-25`), optional OAuth authorizer, and per-request modifier. It implements Streamable HTTP using Foundation URL loading. SDK output shows content variants text/image/audio/resource/resourceLink; `listTools` paginates and `callTool` returns `(content, isError)`. Since the current spec search result is dated `2026-07-28` and describes changed transport/session semantics, the SDK docs' `2025-11-25` default indicates a version alignment question. Pinning the SDK alone is insufficient: verify support/negotiation for the current spec before adoption.
- Official package manifest inspected: `Package.swift` at current `main`, file SHA `273715abe61180310dd181de71afe526d85d9f6b`, declares iOS 16, macCatalyst 16, watchOS 9, Swift tools 6.1, and product `MCP`. This is the best implementation base among sources checked, subject to pinning a reviewed release/tag and validating SDK APIs at that revision.
- Context7's first query attempt with resolved website IDs failed (`Library not found`); querying `/modelcontextprotocol/swift-sdk` succeeded. Official web search also found spec docs: Streamable HTTP POST request / JSON or per-request SSE response behavior; 2026-07-28 spec says it changed behavior (removed GET stream and protocol sessions), while earlier 2025 revisions differ. Therefore avoid custom assumptions based on the older session-ID/SSE transport style.
